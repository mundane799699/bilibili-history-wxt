# 历史记录多次观看与展示模式切换方案（评审稿）

> 状态：Implemented，待浏览器手工验收
>
> 目标版本：待定
>
> 影响范围：历史同步、IndexedDB、历史列表、删除、导入导出、WebDAV、云同步
>
> 评审结论：第 15 节六项决策均采用推荐值
>
> 本文同时作为实现说明与验收依据。

## 1. 结论

新增两种历史展示模式：

| 模式       | 用户看到的含义                             | 示例                                            |
| ---------- | ------------------------------------------ | ----------------------------------------------- |
| 按视频     | 保持现有行为，同一个内容只显示最近一次观看 | 5 月和 7 月看过同一视频，显示 1 条，时间为 7 月 |
| 按观看次数 | 每个被插件观测到的不同观看时间显示一条记录 | 5 月和 7 月看过同一视频，显示 2 条              |

推荐的核心实现不是在切换模式时转换数据，而是：

1. 新增 `historyEvents`，持续保存每次被同步观察到的观看事件。
2. 保留现有 `history` store，继续保存每个内容的最近状态，作为兼容层和“按视频”模式的快速投影。
3. 用户切换模式时只切换查询来源，不删除、不合并、也不复制数据。
4. 升级后默认仍为“按视频”，避免现有用户的列表数量和使用习惯突然变化。
5. 无论用户当前选哪种展示模式，后台都保存观看事件，保证以后随时可切换。

```text
B 站同步结果
      │
      ├── historyEvents：按 business + oid + view_at 保存每次观看
      │                    └── “按观看次数”读取
      │
      └── history：按现有 id=oid 保存最近状态
                           └── “按视频”读取
```

这是一项“数据语义扩展”，但不直接修改现有 `history.keyPath = "id"`，可将迁移和回滚风险控制在较小范围内。

## 2. 需求解释与边界

### 2.1 本方案对“多次观看”的定义

同一内容的 `business + history.oid` 相同，但 B 站接口返回了不同的 `view_at`，就算作不同观看事件。

```text
archive + oid=123 + view_at=1000  → 第一次观看
archive + oid=123 + view_at=2000  → 第二次观看
```

同一内容、同一 `view_at` 被全量同步、增量同步或多设备同步重复拉取时，只保留一条，不能重复计数。

### 2.2 无法补回的历史

插件只能保存 B 站接口实际返回、且被某次同步观察到的状态。若用户在两次同步之间连续看了同一视频多次，而 B 站接口只保留最后一次 `view_at`，中间的观看无法从当前接口重建。

因此需要在产品说明中明确：

- 升级前被现有 `id=oid` 逻辑覆盖的旧观看时间无法恢复。
- 数据库升级时，每条现有 `history` 最多只能生成一条初始观看事件。
- 升级后的记录完整度受同步频率及 B 站接口行为影响。
- 不通过猜测时间或浏览器访问日志伪造观看事件。

### 2.3 同一秒内的重复观看

当前接口的 `view_at` 是秒级时间戳。相同内容在同一秒内产生的两次观看无法可靠区分，本版本按一次观看处理。这是确定性去重规则，不额外生成随机 ID。

## 3. 当前实现及必须调整的原因

### 3.1 当前数据语义

`utils/db.ts` 中：

```text
history
  keyPath: id
  id = item.history.oid
```

后台同步通过 `store.put()` 写入。同一 `oid` 再次出现会覆盖原记录的 `view_at`、进度等字段，所以现有数据库只能回答“最近一次何时看过”，不能回答“看过几次”。

### 3.2 当前增量停止条件不适合观看事件

当前增量同步在一页首尾两个 `oid` 都已存在时停止。对于多次观看：

- `oid` 已存在不代表 `(oid, view_at)` 事件已存在。
- 如果一轮同步中有超过一页的旧视频被重新观看，第一页首尾都可能是已有 `oid`，后续页的新观看时间会被漏掉。

因此不能只新增一个复合主键而保留现有同步停止条件。

### 3.3 当前删除是内容级删除

当前删除函数和删除墓碑都只接收 `id`。在多次观看模式下必须区分：

- 删除某一次观看事件。
- 删除某个内容的全部观看事件。
- 调用 B 站接口删除该内容当前的服务端历史。

这三种行为不能继续共用一个含义模糊的 `deleteHistoryItem(id)`。

### 3.4 当前备份与同步只认识最近记录

以下路径都只调用 `getAllHistory()` 或 `smartMergeHistory()`：

- JSON / CSV 导出。
- 本地目录自动备份。
- WebDAV 手动备份、恢复和自动双向同步。
- 云同步 `/api/history`。
- AI 探索读取最近历史。

如果只改历史页面，这些路径仍会丢弃重复观看事件，必须分别定义兼容策略。

## 4. 数据模型

### 4.1 数据库升级

将 IndexedDB 版本从当前 v7 升到 v8，新增两个 store：

```text
historyEvents
  keyPath: event_id
  indexes:
    view_at
    [view_at, event_id]
    content_key
    [content_key, view_at]

historyTombstones
  keyPath: tombstone_id
  indexes:
    scope
    content_key
    deleted_at
```

保留：

```text
history
  keyPath: id
  indexes:
    view_at
    [view_at, id]
```

不在本功能中迁移 `history` 的主键，以免同时扩大列表、云同步及既有备份格式的兼容风险。

### 4.2 观看事件类型

在 `utils/types/index.ts` 新增：

```ts
export type HistoryDisplayMode = "content" | "visit";

export interface HistoryEvent extends Omit<HistoryItem, "uploaded"> {
  event_id: string;
  content_key: string;
  observed_at: number;
  schema_version: 1;
}
```

字段规则：

```ts
content_key = `${business}:${id}`;
event_id = `${business}:${id}:${view_at}`;
```

- `business` 必须参与键计算，避免不同业务类型使用相同数字 ID 时互相覆盖。
- `event_id` 必须由服务端字段确定性生成，保证重复同步和跨设备合并幂等。
- `observed_at` 记录插件第一次或最近一次观察到该事件的本地毫秒时间，仅用于诊断，不参与观看排序与去重。
- `uploaded` 是现有云上传状态，不属于观看事件本身，不复制到 `historyEvents`。
- 非法或缺失的 `business`、`id`、`view_at` 不写入事件表，并记录可诊断日志。

### 4.3 为什么保留完整事件快照

每条 `HistoryEvent` 保存当时接口返回的标题、封面、作者、观看进度和时长，而不是只保存 `id + view_at`。这样：

- 历史事件不依赖 `history` 当前记录才能展示。
- 删除最近状态后，旧事件仍可完整展示。
- WebDAV 和 JSON 备份可独立恢复。
- 能保留每次观看当时的进度。

代价是存储占用增加。项目已经申请扩展存储保护，本期优先保证数据完整；不默认清理旧事件，并在设置页存储状态中同时展示“视频数 / 观看次数”。

### 4.4 `history` 的定位

`history` 从唯一事实来源调整为“最近观看投影 + 兼容层”：

- 同一内容收到更大的 `view_at` 时更新。
- 收到相同 `view_at` 时允许更新进度、标题等快照字段，但不产生新事件。
- 收到更小 `view_at` 时只补入 `historyEvents`，不能把 `history` 回退成旧状态。
- 新观看时间覆盖已有最近记录时，现有 `uploaded` 应重置为 `false`；相同观看事件的字段刷新可保留上传状态。

所有历史写入必须收口到数据层函数，后台同步和导入逻辑不再直接对 `history` 调用 `put()`。

建议接口：

```ts
upsertHistorySnapshots(items: HistoryItem[], source: HistoryEventSource): Promise<{
  newEvents: number;
  updatedEvents: number;
  updatedLatest: number;
  skippedByTombstone: number;
}>;
```

该函数在同一事务中维护 `history`、`historyEvents` 和墓碑规则，避免两个 store 状态不一致。

## 5. 升级迁移

### 5.1 v8 数据迁移

`onupgradeneeded` 中创建新 store 后，遍历已有 `history`：

1. 校验 `business`、`id`、`view_at`。
2. 为每条合法记录生成确定性的 `content_key` 和 `event_id`。
3. 写入 `historyEvents`。
4. 不修改、不删除原 `history` 记录。
5. 对非法记录只记迁移统计，不能因此中止整个数据库升级。

迁移是幂等的；相同 `event_id` 使用 `put()` 不会重复增加记录。

### 5.2 迁移结果提示

首次升级完成后保存一次迁移报告：

```ts
interface HistoryEventMigrationReport {
  migrated: number;
  skipped: number;
  completed_at: number;
}
```

设置页只在 `skipped > 0` 时提示用户导出备份并查看诊断信息，不因少量异常记录阻止使用。

### 5.3 旧删除墓碑兼容

现有 `DELETED_HISTORY_IDS` 只有数字 ID，没有业务类型和删除时的 `view_at`。数据库升级完成后，在普通运行阶段执行一次惰性迁移：

- 能从 `history` 找到原记录：转换为内容级墓碑，截止时间使用该记录的 `view_at`。
- 已找不到原记录：生成兼容墓碑，按该数字 ID 匹配所有业务类型，截止时间使用升级发生时的秒级时间戳。
- 截止时间之后产生的新观看允许重新进入数据库。
- 至少保留一个版本对旧 `DELETED_HISTORY_IDS` 的读取兼容，确认迁移完成后再清理旧键。

## 6. 同步算法

### 6.1 每页写入

后台将 B 站响应先规范化成 `HistoryItem[]`，再统一调用 `upsertHistorySnapshots()`：

1. 计算 `content_key`、`event_id`。
2. 检查事件级和内容级墓碑。
3. `event_id` 不存在时新增观看事件。
4. `event_id` 已存在时更新同一次观看的快照，不增加计数。
5. 仅当新数据不早于当前投影时更新 `history`。
6. 事务完成后再更新同步进度。

### 6.2 增量停止条件

新增 `HISTORY_SYNC_WATERMARK_VIEW_AT`，保存上一次完整成功同步时第一批数据中的最大 `view_at`。

下一次增量同步：

1. 从最新页开始拉取。
2. 保存所有 `view_at > previousWatermark` 的事件。
3. 对等于水位的记录也执行一次幂等写入，覆盖秒级边界。
4. 一直翻页到当前页最旧的 `view_at < previousWatermark`，再停止。
5. 只有本轮同步正常完成后才推进水位；网络失败不得推进。
6. 继续保留最大页数保护，但触发保护时本轮标记为未完整完成，不能推进水位。

不能再使用“第一页首尾 `oid` 已存在”作为停止依据。

### 6.3 全量同步

全量同步仍然从头遍历到服务端 `cursor.is_end`：

- 已有 `event_id` 幂等更新，不重复计数。
- 服务端当前已不再提供的旧事件不会被删除。
- 全量同步成功后更新水位。
- 全量同步不是“重建”，不能先清空任一历史 store。

### 6.4 首次升级后的行为

升级时由现有 `history` 生成初始事件。升级后的第一次增量同步可直接使用本地最大合法 `view_at` 作为初始水位，并至少重叠读取一页。

不强制所有用户立即执行全量同步；用户手动全量同步时仍能将 B 站当前可见的较旧内容补成初始事件。

## 7. 查询、分页与界面

### 7.1 设置键

在 `utils/constants.ts` 新增：

```ts
export const HISTORY_DISPLAY_MODE = "history_display_mode";
```

取值为 `"content" | "visit"`，默认 `"content"`。

### 7.2 切换入口

在历史页面顶部总数旁增加分段选择：

```text
[ 按视频 | 按观看次数 ]   1,234 个视频 / 2,617 次观看
```

- 选择后立即持久化并从第一页重新查询。
- 保留当前关键词、日期、业务类型、分页/下拉加载设置。
- 切换期间只显示读取状态，不执行迁移或重新同步。
- “按视频”显示“共 N 个内容”。
- “按观看次数”显示“共 N 次观看”。
- 日期筛选在两种模式下都按当前行的 `view_at` 计算；因此同一视频可在观看次数模式下出现在多个日期。

展示模式是历史页的数据语义，建议放在顶部直接可见，不藏到全局设置页。视图设置弹窗继续只管理加载方式和列数。

### 7.3 数据层查询接口

将列表页改为调用统一接口：

```ts
getHistoryPage({ mode, page, pageSize, filters }): Promise<HistoryPage>;
getHistoryAfter({ mode, cursor, pageSize, filters }): Promise<HistorySlice>;
getHistoryCount({ mode, filters? }): Promise<number>;
```

- `content` 路由到现有 `history` store。
- `visit` 路由到 `historyEvents` store。
- 下拉加载游标不能只使用 `view_at`：“按视频”使用 `[view_at, id]`，“按观看次数”使用 `[view_at, event_id]`，避免多条记录时间相同时被 `upperBound(view_at, true)` 一并跳过。
- React 列表 key：`content` 使用 `business:id`，`visit` 使用 `event_id`。
- 分页、筛选和搜索规则保持一致。

### 7.4 卡片表现

按观看次数模式沿用现有卡片，但增加“第 N 次”不是首期要求，因为对升级前数据无法得出真实总次数。卡片只明确展示该事件的观看时间和当时进度。

同一视频的多条事件允许相邻出现，不在首期自动折叠成组，避免与“每次观看算一条”的核心诉求冲突。

## 8. 删除语义

### 8.1 墓碑模型

新增统一墓碑类型：

```ts
interface HistoryTombstone {
  tombstone_id: string;
  scope: "event" | "content" | "legacy-id";
  content_key?: string;
  event_id?: string;
  legacy_id?: number;
  deleted_through_view_at: number;
  deleted_at: number;
  source: "extension-ui" | "bilibili-page" | "import";
}
```

- 事件墓碑精确阻止某个 `event_id` 被 WebDAV 或重复同步恢复。
- 内容墓碑阻止 `view_at <= deleted_through_view_at` 的旧事件恢复。
- 用户以后再次观看，若新 `view_at` 大于截止时间，仍可正常生成新事件。
- 第一版不自动清理墓碑；没有可靠的多设备确认机制前，按固定天数清理会导致旧备份复活。

### 8.2 按视频模式删除

按视频模式中的一张卡代表整个内容，因此删除含义为：

1. 点击后直接删除该内容的全部本地观看记录，不额外弹出确认框。
2. 写入内容级墓碑，截止时间取该内容当前最大的 `view_at`。
3. 删除 `historyEvents` 中该 `content_key` 的全部事件。
4. 删除 `history` 中的最近投影。
5. 若已开启“插件 -> B站 同步删除”，再调用现有 B 站内容级删除接口。

### 8.3 按观看次数模式删除

观看次数模式的卡片垃圾桶只删除当前这一次：

1. 写入事件级墓碑。
2. 删除对应 `event_id`。
3. 如果它正是 `history` 的最近投影，从剩余同内容事件中选取最大 `view_at` 重建投影；没有剩余事件时删除投影。
4. 不自动调用 B 站删除接口，因为 B 站接口是内容级删除，无法准确删除某一次历史事件。

卡片的更多操作可提供“删除该内容的全部观看记录”；该操作复用按视频模式的内容级删除流程，并显示二次确认。

### 8.4 B 站网页删除同步到插件

B 站网页删除消息是内容级操作。启用“B站 -> 插件 同步删除”时：

- 消息必须携带完整 `business + id`，不能只按数字 ID 删除。
- 删除对应内容的全部本地事件和最近投影。
- 生成内容级墓碑，避免 WebDAV 恢复。
- 沿用 `docs/history-data-loss-fix-plan.md` 中“默认关闭、完整校验、可审计”的安全原则。

## 9. 备份、WebDAV、云同步与 AI

### 9.1 JSON 与本地目录备份

历史 JSON 升级为带版本的兼容包：

```json
{
  "formatVersion": 2,
  "exportedAt": "2026-09-08T00:00:00.000Z",
  "history": [],
  "historyEvents": [],
  "historyTombstones": []
}
```

- `history` 保留最近投影，旧版本看到它仍可恢复当前语义。
- `historyEvents` 是完整观看事件。
- `historyTombstones` 防止恢复已删除数据。
- 导入继续兼容旧版 `HistoryItem[]` 和当前完整备份格式；旧数组中的每一条转成一个确定性事件。
- 本地自动备份的“记录数”改为同时保存 `contentCount` 和 `eventCount`，异常保护以两个值都为 0 才判定空库。

CSV 是分析导出而不是恢复格式，按用户当前展示模式导出，并在文件名中加入 `by-content` 或 `by-visit`，避免数量含义不清。

### 9.2 WebDAV

新增 `history-v2.json` 作为新版本权威文件：

```json
{
  "schemaVersion": 2,
  "events": [],
  "tombstones": [],
  "updatedAt": 0
}
```

兼容策略：

1. 新客户端优先下载和合并 `history-v2.json`，事件按 `event_id` 做集合并集，墓碑优先于事件。
2. 同时读取旧 `history.json`，将其中尚未出现在 v2 且未被墓碑阻止的最近记录转成事件，兼容旧客户端产生的新数据。
3. 上传时先写 `history-v2.json`，再写由本地投影生成的旧 `history.json`。
4. 旧客户端仍只会读写 `history.json`，不会破坏 v2 事件文件。
5. 任一文件上传失败都不更新 `WEBDAV_LAST_SYNC`，并明确提示部分同步失败。
6. WebDAV 页面中的“历史记录”一个勾选项同时控制 v1 和 v2 两个文件，不增加用户配置复杂度。

`smartMergeHistory()` 拆为“旧快照兼容导入”和“v2 事件 + 墓碑合并”，不能继续只按 `id` 比较最大 `view_at`。

### 9.3 现有云同步

当前 `/api/history` 很可能仍以 `id=oid` 作为记录语义，扩展端不能直接把多次观看事件发给旧接口，否则会被覆盖、重复计费或导致服务端校验异常。

建议分两期：

- 扩展首期：旧云同步继续上传 `history` 最近投影，并在说明中标注“云端目前按视频保存最近一次；完整观看次数保存在本地/WebDAV备份”。
- 云端二期：新增版本化事件接口，例如 `/api/history-events`，服务端以 `(user_id, event_id)` 唯一，Dashboard 同样提供“按视频 / 按观看次数”切换。接口上线并完成兼容测试后，扩展再上传事件。

云端二期还需要单独确定免费 500 条限制按“视频数”还是“观看次数”计算，本方案不擅自改变计费口径。

### 9.4 AI 探索

AI 探索首期继续读取 `history` 最近投影，避免同一视频多次观看挤占 prompt 条数。后续若增加“重看最多的视频”等分析，再显式读取 `historyEvents`。

## 11. 实施顺序

### P0：数据可保存且不漏同步

1. 新增类型、常量、DB v8 store 和迁移。
2. 实现确定性键、统一双写和投影维护。
3. 将增量停止条件改为成功水位 + 边界重叠。
4. 增加模式化查询和复合游标。

完成 P0 后即使界面仍按视频显示，新的观看事件也已经开始积累。

### P1：用户可切换且可安全删除

1. 增加历史页模式切换和准确计数。
2. 拆分事件级/内容级删除。
3. 增加墓碑、B 站删除消息完整校验和投影重建。
4. 调整删除确认与说明文案。

### P2：备份与多设备完整闭环

1. JSON、本地目录备份升级为 v2 包。
2. WebDAV 引入 `history-v2.json` 并兼容 `history.json`。
3. 补齐跨设备墓碑合并及失败恢复。
4. 完成旧格式导入回归。

P0、P1、P2 应作为同一扩展版本发布，避免事件已经采集但没有完整备份。云端事件同步作为独立后续版本。

## 12. 测试与验收

### 12.1 数据和迁移

- v7 有 100 条不同内容，升级后 `history=100`、`historyEvents=100`。
- 同一 `business + id + view_at` 重复导入十次，观看次数仍只增加 1。
- 同一内容两个不同 `view_at`，按视频为 1，按观看次数为 2。
- 不同 `business` 使用相同数字 ID，不互相覆盖事件。
- 非法 `view_at` 被报告但不阻断其他记录迁移。
- 默认展示模式是按视频，升级后现有列表数量不突变。

### 12.2 同步

- 重新执行全量同步不会重复增加事件。
- 相同事件进度变化只更新该事件快照，不增加次数。
- 超过 30 个已有视频产生新 `view_at` 时，增量同步能跨页捕获，不能在第一页提前停止。
- 网络在中途失败时水位不推进，下次同步可补齐。
- 多条事件 `view_at` 相同，分页和下拉加载均不丢、不重。
- 服务端返回旧快照时，最近投影不回退。

### 12.3 切换和筛选

- 模式切换只改变查询和计数，不改变两个 store 的数据量。
- 切换后保留搜索词、日期和内容类型筛选。
- 日期筛选在观看次数模式中按每次事件时间命中。
- 刷新、手动同步完成后按当前模式重新加载。

### 12.4 删除

- 观看次数模式删除一次，仅少一个事件。
- 删除的正好是最近事件时，按视频投影回退到同内容的上一次观看。
- 按视频模式删除会删除该内容全部事件，并有明确确认。
- 被删除的事件不会被重复增量同步、JSON 导入或 WebDAV 恢复。
- 内容删除后产生更大的新 `view_at` 时，可作为一次新观看重新出现。
- 观看次数模式删除单次事件不会误调用 B 站内容级删除接口。

### 12.5 备份与兼容

- v2 JSON 导出后清库再导入，视频数、观看次数和墓碑一致。
- 旧 `HistoryItem[]` 可导入，并为每条生成一个事件。
- 新客户端可读取只有 `history.json` 的旧 WebDAV 目录。
- 两个新客户端各新增同一视频不同时间的事件，双向同步后双方都有两次观看。
- 一端删除事件后，另一端同步不会使其复活。
- 旧客户端覆盖 `history.json` 后，新客户端的 `history-v2.json` 事件不丢失。

最终验收至少运行：

```bash
pnpm compile
pnpm format:check
pnpm build
pnpm build:firefox
```

仓库暂无自动化测试框架。该功能的数据合并规则风险较高，建议先为“确定性键、投影选择、墓碑裁决、水位停止判断”抽取纯函数，并引入最小单元测试，而不是只依赖浏览器手工测试。

## 13. 回滚策略

- 代码回滚到旧版本时，旧代码会忽略新增 store，现有 `history` 仍可正常展示。
- 不在回滚过程中删除 `historyEvents` 或 `historyTombstones`，避免用户稍后升级时丢失事件。
- `history.json` 继续存在，旧版本 WebDAV 客户端仍可工作。
- 新的 v2 JSON 包保留 `history` 字段，旧导入逻辑可以恢复最近投影，但会忽略事件和墓碑；文档需提示不要用旧版本做完整恢复。
- 如果 v8 迁移失败，保持数据库升级事务原子回滚，不清空 v7 的 `history`。

## 14. 与现有方案文档的关系

`docs/history-data-loss-fix-plan.md` 曾明确“不引入观看事件 ID”，这是当时排查记录数量异常时为控制范围设定的非目标。本方案因新增产品需求引入独立 `historyEvents`，但仍遵守其中以下原则：

- 不修改现有 `history.keyPath = "id"`。
- 不把重看覆盖误判为物理数据丢失。
- 删除需要完整业务类型、墓碑保护和可审计性。
- 同步失败不能推进边界或覆盖唯一备份。
- 数据库升级不能清空原有历史。

实现前应同步更新旧文档的“核心原则/非目标”状态，注明已被本方案扩展，避免维护者以后按旧结论移除事件逻辑。

## 15. 待评审决策

以下是建议默认值，请评审时重点确认：

1. **展示默认值**：推荐默认“按视频”，用户主动切换“按观看次数”。
2. **数据采集**：推荐无论当前展示模式为何，都持续保存事件；否则切换功能会出现不可恢复的空档。
3. **单次删除**：推荐只删本地单次事件，不调用 B 站内容级删除接口。
4. **事件保留期**：推荐首期永久保留，不自动清理；以后再增加可选保留策略。
5. **云同步发布门槛**：推荐不阻塞扩展首期，旧云端暂时只保留最近投影，并在 UI 明示差异。
6. **WebDAV 格式**：推荐新增 `history-v2.json`，而不是直接改变 `history.json` 的数组结构，以兼容旧客户端。

以上六项确认后，方案即可进入任务拆分和实现阶段。
